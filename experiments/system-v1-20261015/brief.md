## 目标

主评分只保留BrowseComp-Plus和EnterpriseRAG-Bench。Enterprise当前使用历史适配器及混合检索，BrowseComp使用当前核心和BM25；首候选v1把这两个主任务统一到当前核心＋BM25／800字符摘录。

**候选能否在两个主基准的夜间评测范围内保持成绩，同时让实现更简单？** 不要求提分，主任务成本最多贵10%；实际升降如实报告。夜间验证BrowseComp dev100与Enterprise dev100/test400，BrowseComp剩余730题在最终版本冻结后再验证。

## 夜间外层调度

本文件定义首次夜间任务和首候选v1；后续候选的完整通用协议见[多基准夜间持续优化循环](protocol.md)。本次只要求编辑方案时不启动模型、GPU或定时任务，运行器和自动接力必须先实现并验证。

### 总预算与停止条件

- 默认从实际启动起运行**8小时**，全夜最多**10,000次sol应用层请求、3个候选（含v1）**。其中9,000次用于主探索、归因和辅助检查，最后1,000次只留给已有答案补判与收尾；各阶段同时受总上限约束。
- 开跑前在 `data/benchmarks/system-nightly/<night_id>/night-plan.json` 冻结起点版本、当前基线、start_at、deadline_at、预算和候选上限；时间显示使用America/Los_Angeles。用户可在开始前覆盖默认值，恢复进程不能重置它们。
- 基线补齐、生成、sol裁判、失败、重试、恢复及Finance辅助调用都进入整夜总账；历史复用不重复计数。Finance虽不影响晋级，仍消耗资源预算。OpenRouter调用及返回费用另记，补判同样受截止时间限制。
- 剩余不足90分钟，或按已观测调用/耗时加20%余量估算无法完成必要评测链路时，不开新候选。最后30分钟不发起生成，只补判和收尾；到deadline_at停止全部实验请求、保存未完成状态。
- 达到时间/预算/3个候选上限、探索额度耗尽、没有有依据的新候选、额度用尽、权限阻塞，或阻断整轮的启动/装配故障两次恢复仍不通时，结束整夜并交付晨报；单题裁判连接失败仍走统一补判规则。不能修改门槛、缩减分母或另开窗口继续凑结果。

### 一轮之后自动做什么

1. v1是第一轮。每轮结束后读逐题差异、错因、工具轨迹和成本，提出一个有证据支持的通用改动，写成下一版本的brief并在调用模型前提交。
2. 下一候选从当前已采用基线开始，不从失败候选继续叠改；先做必要的离线装配验证，再沿用原panel/dev/test、样本和裁判。
3. 候选未通过就保存失败版本和原因，保留当前基线，继续下一候选；通过且有明确收益（提分、降本或实现变简单）才更新当前基线。没有实质收益的持平版本不替换旧基线。
4. 各候选串行、生成并发5、裁判独立1。一次只改通用检索装配、返回内容、提示或工具能力中的一处；本夜不自行换模型、裁判、样本、语料、单题调用上限，不改`src/`，不按题写答案或分支。
5. 外层Codex负责提出和实现下一候选，后台运行器负责评测和记账。真实开启夜间任务时，持续执行或当前聊天续办必须能在阶段完成后自动承接下一步；每10分钟检查一次，无变化不打扰。不能把“后台单轮正在跑”当成连续优化已实现。

### 防止越改越差或越来越贵

- 开夜时固定 `night_anchor`，初始 `current_best=night_anchor=v0`；缺少的基线题按固定配置补齐一次，不能改起点配置。
- **候选必须同时相对current_best和night_anchor通过主门槛。** panel的BrowseComp和Enterprise各自净输不超过2题；主dev200满足每主基准≥−2pp、合并差区间下界≥−2pp、主未缓存输入比≤1.10；Enterprise test400满足同样的点估计、区间和成本条件。Finance/Hotpot不参与这些计算，anchor结果复用，不新增模型调用。
- 因此−2pp和+10%是整夜相对起点的底线，不会每轮累计放宽。每次采用后只更新current_best，anchor和旧结果保持不变。
- 候选用量缺失时成本门槛为undetermined，不晋级；候选完整、基线有用量缺失时可用基线已记录成本下界算保守成本比上界，只有上界≤1.10才通过，不能报告为精确节省率。
- 整夜结束时锁定current_best；没有候选采用就保留v0。后续全量/GPU分数不能反过来触发换候选或继续本夜调参。

## v1 是什么

| 部分 | v1（两个主基准统一） | 现在（v0） |
| --- | --- | --- |
| 运行代码 | 当前核心包：`loop.py`、`codex_adapter.py`、`indexed_rag.py` | Enterprise：`run_frozen.py`恢复历史适配器和检索快照；BrowseComp：当前核心包 |
| 检索 | SQLite FTS5 BM25（标题权重2，现有索引，不重建） | Enterprise：BGE-small＋MiniLM预筛100＋bge-reranker-v2-m3重排＋15条标题预览；BrowseComp：BM25 |
| search每条摘录 | **800字符** | Enterprise4000；BrowseComp A2000、A-lean800 |
| search 返回条数 | 由模型通过 `limit` 自己选，范围 1–20，默认 5（不改） | 同左 |
| read | 不变：按 offset 分页，默认 4000 字符 | 同左 |

**为什么不把默认条数调高：** 轨迹显示，摘录变短后模型自己会要更多条。BrowseComp摘录2000字符时，limit常见为5（40%）和10（32%），只有6%用到20；800字符时变为10（39%）、5（30%）、20（13%）。因此保留原有limit接口与默认值，要几条、读哪篇交给模型；摘录长度是本次统一装配的一项变化。

**BrowseComp 上 v1 就是 A-lean。** 逐字段比对 `data/benchmarks/browsecomp-plus/full-20261015/A-lean/config-dev.json`，确认一致后直接复用 A-lean 的 dev100 结果，不重跑。

## 运行器

本轮是[多基准持续优化循环](protocol.md)的第一个版本：阶段、门槛和计分方法都按那份文档执行。

运行器要满足文档里的"运行器要求"：
- 按题落盘、按题合并；
- 按阶段设请求上限；
- 同时执行阶段预算、整夜预算和截止时间；429只处理出问题一侧，额度或权限错误停止整夜；
- 中断后能续跑。

可以复用 `experiments/browsecomp-full-20261015/` 已经验证过的账本、断点和阶段调度。不要直接用旧评测器的 `--limit` 加 `--resume` 跑分阶段实验：从 30 题续到完整 dev 时，它会因为 config 不同而拒绝续跑。

运行器写好后先做离线验证，不调用模型。至少验证三点：
- 门槛计算能复现 BrowseComp A-lean 对 A 的已知结果（+3.0 pp，区间 [−1, 8]，4 胜 1 负）；
- 到达上限时会停；
- 中断后续跑时请求计数正确。
- 一轮拒绝后能从旧基线自动进入下一候选，一轮采用后能从新基线继续；夜间anchor不变。
- 多轮小幅退步/涨价会被anchor门槛挡住，截止和预算预留会生效，恢复不会重新获得预算。
- 主题集为60/200/400；任意改变Finance/Hotpot分数、成本或缺判状态，都不能改变主评分与晋级；辅助调用仍计入整夜总账。

验证结果写入 `offline-validation.json`。每次门槛判定后更新 [docs/versions.md](versions.md)。

## 开始条件

BrowseComp上一轮必须先完全结束：workflow-state的status为`completed`或`completed_with_budget_or_evaluation_limitations`，completed_phases包含b200和report；最后backfill-state为completed且覆盖A/A-lean/B，最终报告已commit，父进程和阶段子进程均已退出。不要等待不存在的`completed_phases.final_judge_backfill`标记。未结束时只检查与准备，不同时调用sol；当前暂停的巡检不会因编辑方案而自动恢复。

## 阶段 0：离线回放（0 次模型调用）

把 `sota-20261014/enterprise-dev` 轨迹里 sol 实际发出的全部 search（约 321 次），用 v1 的 BM25 加 800 字符摘录原样重放。每次取前 20 篇去重文档，和原轨迹里 cascade 返回的正文加预览文档比较：
- 参考文档覆盖（有 gold 标签的题）；
- 每次 search 返回的字符数。

**这一步只做记录，不作为门槛。** 历史已经证明单次检索召回和最终答对率不一致（一次 BM25 12/24，agent 20/24）。用途是：上线后如果 Enterprise 退步，可以据此判断是不是 BM25 在这些查询上丢了参考文档。

## 阶段 1：双主基准 panel（60题，上限600次请求）

Enterprise按dev文件原顺序取前30题；BrowseComp按 `browsecomp-full-20261015/sample-dev100.json` 原顺序取前30个ID，共60题，固定不换。
- v0两项主基线均已有结果，核对后复用。首候选v1的BrowseComp panel可直接复用同配置A-lean结果，只新跑Enterprise30；后续不同配置必须跑自己的BrowseComp30。
- 候选同时对current_best和night_anchor配对；Finance和Hotpot不进入panel。

**开跑后先排雷：** 第一批轨迹出来后先抽查几题，核对四项：
- 工具没有报错；
- 摘录确实是 800 字符；
- 裁判和计分正常；
- 引用的来源都出现在已检索的结果里。

发现装配问题就停下修复，已经产生的请求照常计数。排雷只查装配，不看分数，不调参数。

**停止条件：** 任一主基准对任一比较基线净输≥3题，就结束本候选，记录原因并返回夜间调度。每项30题只挡明显退步，不直接用于采用。

## 阶段 2：主dev与门槛（200题，上限1,400次请求）

主dev只包含Enterprise100和BrowseComp100，共200题，两个基准各占50%权重。panel是其子集，后续只补各自余下70题；首候选的同配置A-lean100继续复用，不为Finance/Hotpot补基线。

**归因组，仅首候选v1一次，dev通过且资源足够时执行：** 当前核心＋BM25／4000字符、Enterprise dev100，参数与v1相同，只把`--variant v6-e800`换成`--variant v6`；上限700次，计入整夜总账。只解释摘录变化，不参与晋级；对v0仍混合适配器和检索差异，不自动给后续候选重复运行。

**主指标：**
- Enterprise：本地sol裁判正确率。
- BrowseComp：OpenRouter Qwen3-32B准确率。
- Finance/Hotpot不进入主得分、主成本比、主bootstrap或任何采用/淘汰条件。

**统计方法：** 主dev200每题记0/1，Enterprise/BrowseComp各50%，按基准分层bootstrap10,000次、seed20261016。对current_best和night_anchor分别计算，必须两套比较都过关；缺少主判决时不能晋级，辅助缺分不影响判定。

**门槛（预先写死，看结果前不改；阶段 3 的 test 门槛相同）：**

| 条件 | 要求 |
| --- | --- |
| 每个主基准不退步 | 候选减比较基线的点估计≥−2pp |
| 主合并不退步 | 主dev200配对差95%区间下界≥−2pp |
| 主任务成本 | 主dev200的每题平均未缓存输入≤比较基线的1.10倍；不含辅助与裁判用量 |

相对两个基线的三条门槛都满足，才进入阶段3。只有合并区间下界>0时才能说提分，并注明相对哪个基线。

dev 通过后提交一次，v1 就以候选文件和这次 commit 为准冻结，不再改动；门槛结果里会记录 git 版本。然后每个 test 只跑一次：

- 夜间主循环停止提出新候选、current_best冻结后，若时间和预算足够且未进入最后30分钟生成截止窗口，最多给最终版本跑一次Finance dev50，和night_anchor同题比较。缺少的基线dev50只补一次，所有候选/基线生成、裁判、失败和补判共用**500次sol上限**，计入整夜总预算。
